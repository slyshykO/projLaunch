# ProjLaunch — текущая работа над Git GUI

Обновлено 19 ноября 2026 года.
Главная точка входа для всех планов — [AGENTS.md](../AGENTS.md).
Этот файл содержит направление, шаги, состояние работы и всю справку
о реализации этого плана: принятые решения, выполненные пункты и проверки.

## Направление

Новый фокус — довести существующий Git GUI от просмотрщика до полноценного
клиента для повседневной работы с рабочими репозиториями. Сохраняются launcher,
запуск проектов в IDE и работа с local, WSL и SSH через существующий Git-сервер.

Идеи на далёкое будущее собраны в [BACKLOG.md](BACKLOG.md), где сохранена
ссылка на этот план. [CODEX-HANDOFF.md](CODEX-HANDOFF.md) — неизменяемая
историческая справка о работе до перехода на отдельные планы.
Новые результаты по этому направлению записываются только в данный план.

Текущее состояние плана: выполнены stage/unstage целых файлов и создание коммитов.
Создание коммитов дополнено генерацией сообщения через Codex/Claude с выбором
агента в настройках проекта и запуском на endpoint репозитория.
Следующий предложенный этап — работа с ветками; его реализация ещё не начата.

## Отправная точка

Уже работают история и граф, ветки и переходы к коммитам, рабочие изменения,
Staged / Unstaged / Untracked, просмотр файлов и diff, восстановление вкладок,
глубины истории и прокрутки, автоматические Git-подписки.

До начала этого плана операций записи Git не было. Первый этап добавляет
stage/unstage. Нажатие на ветку по-прежнему выбирает её tip для просмотра.

## Предварительная последовательность

Пользователем выбрано направление развития. Следующая декомпозиция — предложение
для последовательных задач; точный состав и порядок ещё не утверждены.

1. **Подготовка изменений — выполнено 25.10.2026:** stage/unstage целых файлов,
   выбранных наборов и групп из панели рабочих изменений; обновление статуса и diff.
2. **Создание коммитов — выполнено 18.11.2026:** сообщение коммита, обзор подготовленных изменений,
   выполнение commit и понятное отображение результата или ошибки.
3. **Работа с ветками:** создание, переключение и удаление веток; понятное
   поведение при незакоммиченных изменениях и конфликтах.
4. **Синхронизация с remote:** fetch, pull, push, выбор remote/upstream,
   отображение прогресса и расхождения историй.
5. **Временное сохранение работы:** создание и просмотр stash, apply/pop/drop.
6. **Интеграция изменений и конфликты:** merge/rebase, список конфликтов,
   переход к их разрешению, продолжение и отмена начатой операции.

Идеи дополнительных возможностей после основного сценария вынесены в
[BACKLOG.md](BACKLOG.md#дополнительные-возможности-git-gui).

## Подход к реализации

- Делать законченными шагами: UI-действие, типизированный IPC/RPC, выполнение
  на нужном endpoint, обработка ошибок и обновление состояния после операции.
- Сохранить выбор, прокрутку и открытые diff там, где они остаются актуальными.
  Учитывать события watchers и поздние ответы параллельных запросов.
- Для операций, затрагивающих рабочие файлы или историю, явно показывать область
  действия и последствия; ошибки не должны приводить к скрытому сбросу изменений.
- Проверять операции на временных репозиториях и изолированных UI fixtures.
  Проверки должны включать изменения index/worktree и состояния репозитория,
  а не только успешный ответ команды.
- Постоянные repository bindings и отдельный HTTPS/WSS API не являются
  предварительными условиями этой работы.

Первый этап использует существующие группы рабочих изменений и подготавливает
интерфейс к созданию коммитов. Последующие этапы начинать по выбранной задаче пользователя.

## Реализация, решения и результаты

### Release-команда build set-version — выполнено 19.11.2026

**Согласованный состав.** Для `set-version X.Y.Z` пользователь запросил проверку
чистого Git checkout и ветки `main`, затем отправку release-коммита и тегов.

**Реализация и решения.** До изменения файлов проверяются текущая ветка и
`git status --porcelain=v1 --untracked-files=all --ignore-submodules=none`.
Detached HEAD, другая ветка, staged/unstaged изменения, untracked-файлы и даже
version-only изменения отклоняются; ignored build outputs не мешают релизу.
Существующие проверки формата, коллизий тегов и возрастания версии сохранены.
После release-коммита и локального тега последовательно выполняются `git push`
и `git push --tags`, с обычными настройками remote/upstream пользователя.
Отправляются все локальные теги, как запрошено. При ошибке первого push второй
не выполняется. Ошибка любого push сохраняет локальный коммит и тег и сообщает,
как повторить push без повторного `set-version`. Обновлены CLI help и руководства
Development/Testing.

**Проверки.** Fantomas и `npm run gen:version` выполнены.
`dotnet fsi --exec build/scripts/Versioning.Tests.fsx` прошёл: изолированный
bare remote подтверждает публикацию коммита и всех тегов, отказ на другой ветке
и detached HEAD, staged/unstaged/untracked/version-only изменения без мутаций,
ошибку branch push без отправки тегов и конфликт remote tag после успешного
branch push. Существующий fixture commit hook получил Unix execute bit для
проверки отказа hook на Linux. `dotnet build build/build.fsproj --no-restore
--disable-build-servers -m:1 -nr:false` прошёл для net10.0 и net11.0 без warnings
и errors; первоначальная sandbox-сборка зависла после сообщения о недоступном
MSBuild server, повторная сборка выполнена вне sandbox. `git diff --check`
с `cr-at-eol` прошёл. Реальный remote проекта не изменялся.

**Ограничения.** Push-команды не атомарны: коммит может уже находиться на remote,
если отправка тегов завершилась ошибкой; Git также может принять часть тегов.
Remote/upstream должен быть настроен заранее. Проверка максимальной версии,
как и раньше, использует локальные теги; автоматического fetch нет.

### Генерация сообщения коммита через Codex/Claude — выполнена 18.11.2026

**Согласованный состав.** Пользователь запросил выбор Codex/Claude в настройках
проекта и правило prompt: при наличии Staged описывать только подготовленные
изменения, иначе использовать весь diff. Отдельно выбрано выполнение агента
на endpoint репозитория: local, внутри WSL или на SSH-host.

**Поведение.** Edit project содержит Commit message agent: None / Codex / Claude.
В Uncommitted changes появились Generate with Codex/Claude, Cancel generation
и переход к Project settings. Результат заполняет редактируемое сообщение;
stage и commit выполняются пользователем отдельно. Prompt явно содержит правило
Staged/all; сервер сам собирает подходящий snapshot. При отсутствии Staged
включены tracked diff и untracked text previews; бинарные файлы обозначены
без передачи их содержимого. При ошибке или отмене прежнее сообщение сохраняется.

Открытие через карточку выбирает настройки соответствующего проекта. Для общего
или восстановленного repo с несколькими проектами доступен явный выбор проекта.
Используются текущие discovery roots с endpoint identity; постоянные repository
bindings не добавлялись. Смена проекта/агента, ручное редактирование сообщения,
watcher invalidation и закрытие вкладки защищены request-generation guards.
Отмена до завершения repo.open не запускает агента; после старта отправляется
`git.cancel`. Закрытие вкладки тоже запрашивает отмену. Во время генерации
Stage/Unstage и Commit заблокированы. На сервере после ответа агента повторно
сравнивается diff, поэтому изменение snapshot обнаруживается и без watcher.

**Хранение и протокол.** Опциональное project JSON поле `commitAgent` хранит
`codex`/`claude`; Rust enum отвергает произвольные программы. SQLite migration
0004 добавляет `commit_agent_json` с исходным JSON null. Старые проекты получают
None; настройка сохраняется после перезапуска и обновления lastOpened. Workspace
JSON остаётся v3. Добавлены typed IPC `git_generate_commit_message` и additive v1
RPC `git.generateCommitMessage`, принимающий repoId/operationId/agent и возвращающий
message/scope. Frontend работает только через `AppTauri.Git`.

**Выполнение.** Используются установленные и авторизованные CLI из PATH endpoint.
Они запускаются без shell в отдельном временном каталоге с prompt через stdin.
Codex exec использует read-only sandbox, ignored user config/rules, отключённые
shell/apps/delegation/hooks/search и файл final message. Claude print использует
JSON result, отключённые tools/MCP/slash commands/hooks и no-session-persistence.
Авторизация остаётся в окружении CLI; приложение не хранит ключи. `tempfile`, ранее
тестовая зависимость сервера, перенесён в runtime dependencies для временного
каталога/final-message файла. Сохраняется общий runner с отменой, ограничением
вывода и завершением child process. Лимиты: context 256 KiB (без молчаливого
обрезания текста), сообщение 65536 UTF-8 bytes, 2 concurrent agents/server,
120 секунд на CLI, 150 секунд на RPC и 180 секунд client deadline только для
этого метода. Общие Git deadline не изменены.

**Проверки.** Стандартный `npm run build` (release sidecar + Fable/Vite) и Fable
Debug прошли; все 25 frontend regression-скриптов прошли. Новый сценарий проверяет
настройки общего repo, local/WSL/SSH routing, заполнение сообщения без commit,
ручные изменения/поздние ответы, watcher/settings invalidation, ошибки, cancel,
закрытие вкладки и отмену во время открытия repo. Rust Git workspace: 41 тест
прошёл, включая реальные Git/RPC со fake Codex/Claude executables: staged-only
и all input, binary summaries, сохранение index/HEAD/worktree, отказ агента,
пустой результат, изменение repo во время генерации и отмена. Native: 46 тестов
прошли, 2 штатно пропущены; проверены migration v3→v4, legacy default, сохранение
обоих агентов после рестарта и запрет неизвестных значений. Rust-прогоны используют
TMPDIR=/var/tmp из-за служебного /tmp/.git; единичный Text file busy в тесте
packaged sidecar исчез при повторном прогоне после сборки. Git workspace Clippy
с `-D warnings`, Fantomas, cargo fmt и diff whitespace check прошли.
Build hooks синхронизировали семь manifests/lockfiles до
`0.5.2+17.gc910d4d.dirty`; версии сохранены вместе с изменениями.
README, user guide, architecture/testing/remote guides и server API обновлены.

**Ограничения.** Live model API, действительная авторизация Codex/Claude,
Windows launcher и настоящий запуск генерации на WSL/SSH вручную не проверялись;
тесты используют локальные изолированные fake CLI и endpoint IPC stubs.
Нужны актуальные CLI с используемыми флагами, настроенная авторизация и PATH
неинтерактивного endpoint процесса. Выбор модели, кастомный prompt, использование
repository-local agent instructions, автоматические stage/commit и сохранение
draft между перезапусками не входят в задачу. Отмена после старта best-effort;
поздний ответ в любом случае не применяется. All-diff сообщение нужно проверить
после выбора файлов для Staged, если в коммит включается только часть изменений.

### Исправление переполнения stderr агента — выполнено 18.11.2026

**Причина.** При реальном запуске Codex генерация завершалась ошибкой
`Git stderr exceeds 65536 bytes`: общий GitRunner считал диагностический поток
агента ограниченным потоком ошибок Git и убивал процесс после 64 KiB.

**Изменение.** Для Codex/Claude включён отдельный режим чтения stderr:
поток полностью дренируется, в памяти хранится только последний фрагмент до
64 KiB. При ненулевом exit code показывается конец диагностики с отметкой
об отброшенном начале; длинный progress/prompt echo больше не прерывает
успешную генерацию. Лимиты stdout/final message, timeout и cancellation остаются;
обычные Git-команды сохраняют прежний жёсткий stderr limit. Ошибки агента теперь
называют Agent вместо Git, а общий wrapper больше не предлагает переустановку
и авторизацию независимо от фактической причины отказа.

**Проверки.** `cargo test --manifest-path crates/Cargo.toml -p git-server --locked`:
35 тестов прошли. Fake Codex/Claude RPC fixture теперь выдаёт 192 KiB stderr
перед успешным результатом и перед ошибкой; проверены сохранение последней
ошибки, ограниченный размер диагностики и отсутствие отброшенного префикса.
Новый runner-тест проверяет timeout/cancel после превышения 64 KiB;
существующая проверка строгого stderr limit для Git тоже прошла.
Git workspace Clippy `--all-targets --all-features --locked -- -D warnings`,
`cargo fmt`, `npm run gen:version` и `npm run build` прошли. Release Linux sidecar
пересобран; версия остаётся `0.5.2+17.gc910d4d.dirty`. Ранее накопленные изменения
функции и manifests/lockfiles сохранены. Реальный model API не вызывался;
проверки используют изолированные CLI fixtures. Для применения нужно перезапустить
desktop/Git server, использующий обновлённый sidecar.

### Этап 2. Создание коммитов — выполнен 18.11.2026

**Поведение.** В Uncommitted changes добавлена форма сообщения с многострочным
описанием и кнопкой Commit staged. Показаны ветка назначения, первый коммит или
предупреждение о detached HEAD, число подготовленных файлов и явное указание,
что коммит включает весь Staged независимо от checkbox-выборки Stage/Unstage.
Подготовленные изменения просматриваются через существующие группы и diff.
Пустое сообщение, отсутствие Staged, неизвестный статус и конфликты блокируют
создание. После успеха показан полный OID и очищено сообщение; при ошибке
сообщение сохраняется. Черновик и результат привязаны к endpoint/worktree,
переживают переключение, закрытие и повторное открытие вкладки в текущем сеансе.

**Решения.** Типизированные IPC `git_commit` и дополнительная capability v1
`git.commit` принимают сообщение и ожидаемые HEAD/ветку, возвращают OID.
Репозиторий заново открывается по корню перед записью; transport остаётся
в `AppTauri.Git`. Сервер проверяет сообщение (непустое, без NUL, до 65536 UTF-8
байт), HEAD/ветку, конфликты, наличие подготовленных изменений и отсутствие
merge/rebase/cherry-pick/revert/sequencer в фактическом gitDir worktree.
Используется `git commit --no-edit --cleanup=whitespace --file=-`: сообщение
передаётся через stdin без shell, сохраняются строки с `#`, настройки автора,
hooks и подписи endpoint. Автоматического staging, amend и обхода hooks нет.

Commit и Stage/Unstage используют общий `pendingGitWrites` / `gitWriteRequestId`
по endpoint/worktree, включая закрытые вкладки. Watchers накапливают invalidations,
а поздний diff до записи отвергается. После успеха **и ошибки** явно перечитываются
история, ветки, статус и рабочие diff; история получает свежий cursor с сохранением
загруженной глубины и scroll anchor. Открытый diff следует за оставшимися изменениями
файла. Повтор возможен только вручную после проверки истории: при обрыве связи
коммит мог уже создаться. Обычное закрытие окна ждёт завершения Git-записей.
Миграции БД и workspace JSON не потребовались; черновики между перезапусками
приложения не сохраняются.

Исправлена обнаруженная гонка GitRunner: при раннем завершении Git с закрытием
stdin сохраняется и показывается исходная ошибка stderr, например index.lock,
вместо случайного `Broken pipe`. Отдельный тест проверяет этот путь.

**Проверки.** `npm run build` (release Linux sidecar + Fable/Vite) и компиляция
Fable Debug прошли. Все 24 frontend regression-скрипта прошли; новый
`test-create-commit.mjs` проверяет разметку, валидацию, local/WSL/SSH routing,
свежий runtime repoId, блокировку повторных/конкурирующих записей, поздние ответы,
обновление истории/веток/diff, ошибки, сохранение черновика и закрытие окна/вкладки.
Git workspace: 40 тестов прошли, включая четыре новых real-Git/RPC сценария
создания коммитов и тест раннего закрытия stdin. Проверены точное дерево и родители
коммита, Unicode/многострочное сообщение, частичный index, удаления/переименования,
binary/untracked, unborn/detached HEAD, смена ветки/HEAD, пустые сообщения и индекс,
конфликты, operation markers, чужой index.lock, identity, hooks и signing failures.
Нативные тесты: 45 прошли, 2 штатно пропущены (SSH и helper).
Rust-прогоны использовали `TMPDIR=/var/tmp`: служебный `/tmp/.git` в песочнице
мешает существующим discovery fixtures. Git workspace Clippy с `-D warnings`
прошёл. Fantomas / cargo fmt выполнены. Build hooks синхронизировали семь
manifests/lockfiles до `0.5.2+16.g661e055.dirty`; изменения версий сохранены.
Обновлены README, пользовательская, архитектурная, тестовая и серверная справки.
`git diff --check` с `cr-at-eol` прошёл; frozen handoff не изменён.

**Ограничения.** Только обычный коммит всего index; amend, empty commit,
выбор автора и продолжение интеграционных операций не входят в этот этап.
Предварительная проверка HEAD/ветки не блокирует внешние Git-клиенты: индекс
может измениться после просмотра, hooks также сохраняют обычную семантику Git.
OID считывается из HEAD после успеха; внешнее перемещение HEAD в этот промежуток
может повлиять на возвращённый OID. Сохраняется общий таймаут Git-команды 30 секунд;
интерактивные hooks/подпись требуют внешней настройки. Desktop GUI вручную и
создание коммитов на настоящих WSL/SSH endpoint в этой задаче не проверялись.

### Этап 1. Stage/unstage целых файлов — выполнен 25.10.2026

**Поведение.** В Staged есть Unstage, в Unstaged / Untracked — Stage.
Доступны кнопка в строке, независимые checkbox-выборки по группам,
действия selected и all с количеством файлов. All относится только к своей
группе. Нажатие на имя файла открывает diff, а checkbox задаёт набор для записи.
Операции проходят через тот же endpoint для local, WSL и SSH.

**Решения.** Добавлены типизированные IPC `git_stage` / `git_unstage` и RPC
`git.stage` / `git.unstage`, объявленные как дополнительные capabilities
протокола v1. Сервер сверяет пути с актуальной группой diff, самостоятельно
добавляет исходный путь переименования, отвергает пустую/устаревшую выборку
и расширение пути на посторонние изменения в подкаталоге. Предел — 10000 путей
на запрос, дополнительно действует существующий лимит RPC frame.
Пути передаются буквально, через NUL-разделённый stdin: один запуск Git на набор,
без shell и ограничений длины командной строки Windows.

Stage использует `git add --all` для выбранных путей, включая удалённые файлы;
у частично подготовленного файла индекс заменяется текущим содержимым worktree.
Unstage использует файловую форму `git reset`: она работает и до первого коммита,
не меняет HEAD и рабочие файлы. Submodule stage обновляет gitlink, а не содержимое
вложенного репозитория. Подготовка конфликтного файла отмечает его разрешённым;
UI явно предупреждает об этом в группе. `--hard`, force и удаления чужих index.lock нет.

Повторная запись блокируется по endpoint + корню worktree, даже если вкладку
закрыли и открыли снова. Это временное состояние не сохраняется в workspace JSON.
Watchers продолжают накапливать invalidations; обновление вкладки откладывается
до ответа записи. Поздний ответ diff, начатого до записи, не применяется.
После успеха **и ошибки** выполняется явное обновление статуса и групп файлов,
независимо от доступности watcher. Открытый diff перечитывается и следует за файлом
в новую группу, если путь остаётся; загруженные страницы истории и прокрутка
сохраняются. Текущие строки и diff остаются смонтированными при автоматическом
перечитывании. Ошибка записи остаётся видна, повтор выполняется только вручную:
при обрыве связи нельзя предполагать, что Git не успел изменить индекс.
Блокировка SQLite относится к каталогу проектов и не запрещает Git-операции;
конкуренцию с другими Git-клиентами контролирует штатный index.lock Git.

**Проверки.** Git workspace: 34 теста прошли (в том числе 5 новых real-Git/RPC
сценариев); дополнительно проверено stage разрешённого merge-конфликта.
Проверены содержимое index/worktree/HEAD, частичная подготовка, удаления, бинарные
и Unicode/literal-пути, unborn HEAD, переименование, ошибочная/устаревшая выборка,
замена файла каталогом и чужой index.lock. Все 23 frontend regression-скрипта
прошли; новый `test-index-changes.mjs` проверяет группы, endpoint routing,
watcher/read races, повторные нажатия, ошибки и закрытие/переоткрытие вкладки.
Нативные тесты: 45 прошли, 3 opt-in/helper пропущены; WSL-тест отдельно запущен
на Ubuntu и прошёл, включая stage/unstage Unicode-файла и сохранение его содержимого.
Clippy обоих Cargo workspace с `-D warnings` прошёл. Fantomas / cargo fmt выполнены.
`npm run build` и Linux sidecar `build-git-server ubuntu22 --release` собраны.
В изолированной браузерной fixture проверены checkbox-выбор нескольких файлов,

**Ограничения.** Только целые файлы, без hunk/line staging и создания коммитов.
Выбор каталогов не поддерживается; переход «файл → каталог» с пересекающимися
изменениями может потребовать внешнего Git-клиента. Внешние изменения между
показом списка и выполнением Git не блокируются; Stage берёт текущую версию файла.
Проверка SSH ограничена frontend routing и общим RPC: отдельный настоящий SSH-хост
в этой задаче не использовался.
