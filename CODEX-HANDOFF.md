# ProjLaunch — продолжение разработки

Обновлено 25 октября 2026 года. Этот файл — общая точка продолжения работы
между ПК и чатами. Он хранится в Git в корне репозитория. Все пути ниже
относительны корню checkout, независимо от диска, имени пользователя и ОС.

Репозиторий: [slyshykO/projLaunch](https://github.com/slyshykO/projLaunch).
Актуальные инструкции по сборке: [README.md](README.md).
Контракт Git API: [crates/git-server/README.md](crates/git-server/README.md).

## Восстановление истории и прокрутки (25 октября 2026)

Workspace JSON v3 сохраняет для каждой вкладки количество загруженных коммитов,
вертикальное/горизонтальное смещение и OID верхнего видимого коммита со смещением
внутри строки. v1/v2 читаются без этих полей; SQLite-схема остаётся версии 3.
Сами страницы, patches и runtime repoId/cursor не сохраняются: восстановление
открывает новую Git-сессию и последовательно читает страницы до прежней глубины
или конца истории. Фоновые вкладки по-прежнему загружаются при выборе.

Переключение вкладки приостанавливает догрузку после текущего read; возврат её
продолжает. Cancel, ручная прокрутка или выбор commit/branch прекращают восстановление.
Ошибка оставляет прежние depth/scroll для Retry через Refresh с новым snapshot;
закрытие во время догрузки тоже сохраняет цель. Обычный Refresh после завершения
восстановления по-прежнему начинает историю с первой страницы.
Прокрутка применяется после загрузки и появления панели (в том числе после закрытия
восстановленного diff). Если anchor присутствует в загруженных страницах, используется
его новое положение; иначе pixel offset ограничивается доступной высотой/шириной.
Изменения scroll сохраняются с задержкой 200 мс; закрытие ждёт актуальный workspace save.

Регрессии: `test-history-restoration.mjs`, `test-history-scroll.mjs`, Rust workspace
validation и SQLite roundtrip. Проверены Fable/Vite, frontend-регрессии, 41 native-тест
(3 ignored, включая opt-in WSL/SSH), Clippy, Fantomas и cargo fmt. В браузере на
изолированном IPC fixture проверены reload с 300 коммитами и точной прокруткой,
ленивая вторая вкладка с 200 коммитами и возврат из восстановленного diff.
Нативный WebView для этого изменения не запускался; пользовательская БД не использовалась.

## Проверка повышения версии (22 октября 2026)

`set-version X.Y.Z` отклоняет версии не выше максимального локального релизного
тега (`vX.Y.Z` или `X.Y.Z`) до изменения файлов, индекса и refs. Компоненты
сравниваются как числа; ближайший тег после ошибочного понижения не уменьшает
этот порог. Теги других веток тоже учитываются, prerelease/посторонние — нет.
При отсутствии релизных тегов можно создать первый релиз.
`build.bat version` выводит одну строку текущей Git-версии в формате About,
включая расстояние/hash и `+` при tracked-изменениях. Синхронизация манифестов
и создание коммитов/тегов не выполняются. Проверки — `Versioning.Tests.fsx`.

## Запуск WSL из сборщика (22 октября 2026)

При периодическом сбое `wslpath` пользователь наблюдал код `-1073740022`
(`0xC000070A`) ещё до запуска Linux-компиляции. Точное падение при проверке
не воспроизвелось; обнаружена потеря вывода WSL из интерактивной консоли.
`GitServerProcess.fs` запускает команды сборки с перенаправлением всех трёх
стандартных потоков вместо наследования консольных handles при `CreateNoWindow`.
stdin сразу закрывается, stdout/stderr читаются параллельно, логи передаются
в текущую консоль. При ошибке сохраняется захваченный stdout и показывается
также hex-код завершения. Это устраняет зависимость от консольных handles;
устранение именно периодического падения пока требует подтверждения.
Регрессия: `dotnet fsi --exec build/scripts/GitServerProcess.Tests.fsx`.
Проверены полная `build.bat build --release` с созданием ZIP, отдельный WSL-этап
из интерактивной консоли, тесты аргументов Git-сборщика и self-build.

## Git через SSH (22 октября 2026)

Добавлен Endpoint Ssh { host, username }: отдельные IP/host + username или alias
из OpenSSH config с пустым username. Явный username передаётся через `-l`, иначе
OpenSSH сам выбирает User. Порт, IdentityFile, ProxyJump задаются в обычном SSH
config. Формат ProjectData.remote и SQLite-схема не меняются. Вкладки сохраняют
endpoint, различаются по host/user/root и подписаны SSH-адресом.

`src-tauri/src/ssh.rs` запускает системный OpenSSH без PTY и интерактивных запросов.
Требуются ключ/agent и доверенный host key в known_hosts. Ошибки авторизации и
проверки ключа показываются пользователю. Используются отдельные процессы SSH
без общего ControlPath, перенаправления портов или фонового режима.

Установщик вынесен из WSL в `src-tauri/src/remote_server.rs` и
`src-tauri/src/remote/bootstrap.sh`; оба транспорта используют проверку SHA-256,
версии/протокола и атомарную установку одного Linux x86_64 glibc-бинарника.
Удалённые Windows/macOS/ARM64 пока не поддерживаются. RPC идёт через stdio,
remote daemon/TCP-порт не нужны. Поиск workspace/репозиториев выполняется удалённо.

Проверены Fable/Vite, 17 frontend-скриптов, 40 native-тестов и Clippy. Реальный
SSH-тест выполнен Windows OpenSSH → временный sshd в WSL с отдельными ключами:
как config alias, так и user + IP, неизвестный host key, отказ авторизации,
установка/повторное использование/повреждение, версия/протокол, quoted/Unicode
пути, Git RPC, reconnect и завершение remote PID. WSL regression тоже прошла.
Тесты: `scripts/tests/test-ssh-endpoints.mjs`, opt-in Rust
`ssh_install_reuse_repair_rpc_and_shutdown`; запуск описан в README Git-сервера.

## Git в WSL (22 октября 2026)

Реализован Endpoint Local/WSL: существующий `ProjectData.remote` задаёт среду,
`path` остаётся путём внутри неё. Отдельная таблица endpoints пока не нужна.
GitHost держит отдельный stdio-клиент на дистрибутив; все Git IPC-запросы получают
endpoint рядом с params. Вкладки различаются по endpoint + root и показывают WSL.
Workspace JSON начиная с v2 сохраняет endpoint вкладок и активной вкладки;
текущая v3 также хранит глубину истории/scroll, v1 читается как локальное состояние.
Версия SQLite для этих изменений не менялась.

`src-tauri/src/wsl.rs` и общий `remote/bootstrap.sh` доставляют bundled Linux sidecar через
stdin в `~/.local/share/projlaunch/git-server/<sha256>/`. Проверяются SHA-256,
`--version-json`, target и protocolVersion. Неизменённый бинарник не копируется;
повреждённый восстанавливается атомарно. Разные сборки имеют отдельные каталоги.
Сервер запускается `wsl.exe --distribution <name> --cd ~ --exec <server> stdio`;
TCP-порт и установка Rust не нужны, Git требуется в PATH дистрибутива.
На выходе закрывается stdin, сервер завершает дочерние процессы; WSL не выключается.

Обнаружение workspace/solution вынесено в `crates/git-discovery`; новый RPC
`project.discover` выполняет его внутри Linux (WSL и SSH).
Регрессии: `scripts/tests/test-wsl-endpoints.mjs`, native workspace tests и opt-in
`wsl_install_reuse_repair_rpc_and_shutdown` (переменная `PROJLAUNCH_TEST_WSL_DISTRO`).
Последний проверяет реальный WSL в изолированном `/tmp`, включая обновление,
восстановление файла, quoted/Unicode paths, RPC, reconnect и завершение процесса.
Проверены Fable/Vite, 16 frontend-скриптов, 38 native-тестов и отдельный WSL-тест,
25 тестов Git workspace, Clippy обеих Rust-частей с `-D warnings`. Linux release
собран ubuntu22-скриптом; реальная проверка выполнена в установленном Ubuntu WSL.

## С чего начать на другом ПК

1. Получить актуальную ветку репозитория, открыть её корень как рабочую папку.
   Проверить `git status` и последние коммиты. Сохранять локальные изменения
   пользователя; не заменять checkout копией с другого ПК.
2. Прочитать этот файл, применимые AGENTS.md, README и руководство Git-сервера.
   Считать исходники и lock-файлы источником текущего состояния.
3. Установить зависимости, перечисленные в README: Node/npm, Git, Rust,
   .NET SDK из `global.json`, .NET 10 runtime и Windows/Tauri prerequisites.
   Версии пакетов определяют manifest/lock-файлы, а не этот документ.
4. Из корня выполнить `npm ci`, `dotnet tool restore`, `dotnet paket restore`.
   Локальный Paket закреплён в манифесте инструментов; старый Paket 11.0.1
   не восстанавливает net11.0. Не менять версии только ради обхода среды.
5. Для разработки использовать `npm run tauri dev`. Для сборки Windows —
   `build.bat build` (debug) или `build.bat build --release`.
   Для сборки с последующим запуском: `build.bat run` или `build.bat run --release`.
   Команда ждёт закрытия приложения; при ошибке сборки запуск не выполняется.
   `build.bat` при необходимости пересобирает собственный F# helper.
6. Для следующей задачи использовать раздел «Следующий этап» ниже.
   После завершённого этапа обновлять этот файл вместе с кодом.

Для продолжения достаточно checkout и обычного восстановления зависимостей.
Старые папки прототипов, копия SQLite-проекта, патч переноса и кеши из локальной
папки Codex больше не нужны. Не применять старые скрипты переноса повторно.
`target`, `node_modules`, `bin`, `obj` и sidecar-бинарники генерируются на новом ПК.

SQLite-каталог проектов и пользовательские настройки приложения остаются
локальными в app-data и не синхронизируются через Git. Пути launcher-проектов
могут различаться на разных ПК. Этот handoff переносит контекст разработки,
а не пользовательскую базу.

## Что уже готово

Добавлена субкоманда `build.bat publish [--wsl-distro NAME]`; `build.bat build --release`
использует тот же путь публикации. Сначала собирается Linux Git server в WSL,
затем release GUI/native sidecar через существующий Tauri build. ZIP:
`build/dist/projLaunch-<version>-windows-x64.zip`. В корне `projLaunch.exe`,
в `binaries/` два сервера с target triple в имени, без дополнительной корневой папки.
`Publish.fs` включён в build.fsproj. Пакуется явный список трёх файлов;
проверяется наличие/ненулевой размер, временный ZIP заменяет предыдущий только
после успешного завершения. Обычная debug-сборка остаётся без WSL/архива.
Публикация поддерживает Windows x64, стандартные Cargo output paths и WSL.
GUI сначала ищет свой сервер в `binaries` рядом с executable, затем adjacent
legacy sidecar, затем checkout. Linux-бинарник автоматически доставляется и
запускается в WSL/SSH endpoint (см. разделы выше). Tests проверяют ZIP layout/extraction,
непопадание лишних файлов, сохранение предыдущего ZIP при ошибке, а также запуск
настоящего сервера из portable layout при недоступном checkout.
Проверены обе команды целиком: `publish --wsl-distro Ubuntu` и `build --release`.
После одиночного сбоя rustc на зависимости symlink повтор выполнен с
`CARGO_BUILD_JOBS=2` успешно. ZIP распакован: ровно три файла, SHA256 совпадают
с release-артефактами; извлечённый Windows server прошёл hello/EOF shutdown.
Прошли 4 теста git_host, Publish.Tests.fsx и GitServer.Tests.fsx, сборка helper,
Fable/Vite в составе release build, Fantomas, cargo fmt и diff check.
GUI из архива не запускался, пользовательская БД не затрагивалась.

Добавлена отдельная сборка Git-сервера для Ubuntu 22.04:
`build.bat build-git-server ubuntu22 --release [--wsl-distro NAME]`.
`GitServerUbuntu22.fs` включён в `build.fsproj`; Windows запускает скрипт через
WSL выбранного дистрибутива (по умолчанию default), Linux запускает Bash напрямую.
Скрипты находятся в `build/scripts/build/`, используют Zig как linker/C compiler
с `x86_64-linux-gnu.2.35` по образцу vmssrv-mock. Проверяется максимальная версия
GLIBC symbols; результат новее 2.35 не копируется. Cargo cache изолирован в
`crates/target/ubuntu22`, итог — `src-tauri/binaries/project-launch-git-server-x86_64-unknown-linux-gnu`.
Все бинарники лежат непосредственно в `binaries` с target triple в имени;
debug/release заменяют один итоговый файл, как у native-сборки.
Обычная native-сборка не требует WSL. Артефакт входит в portable ZIP;
доставка в WSL/SSH реализована, установка через installer не реализована.
Shell scripts закреплены с LF. Инструменты нужны внутри Linux: Rust/rustup,
Zig (PATH, ZIG_BIN или ~/bin/zig*), readelf. Build helper проверяет аргументы,
пути передаются отдельными аргументами, без shell interpolation.
Проверена настоящая release-сборка Windows → WSL Ubuntu 24.04, Zig 0.15.2;
ELF требует максимум GLIBC_2.34. RPC smoke на временном репозитории в WSL прошёл:
hello/open/status/branches/EOF shutdown. Запуск непосредственно на Ubuntu 22.04
пока не проверен; совместимость glibc не означает поддержку Alpine/musl или ARM64.
Проверены команда build.bat целиком с пересборкой helper, сборка build.fsproj,
`GitServer.Tests.fsx` (аргументы/пути с пробелами/неверные параметры), Fantomas,
Bash syntax и diff check. Существующий version hook синхронизировал manifests.

Ошибки файловых операций содержат проблемный путь и исходную причину: поиск
проектов и `.git`, чтение diff/preview, создание логов, блокировка и операции SQLite,
поиск/запуск Git sidecar и запуск IDE. Путь базы добавляется также на границе
storage worker, поэтому он сохраняется в IPC и frontend-логе. Формат отмены Git
сохранён. Регрессии проверяют передачу путей через storage/RPC, включая пропавший
файл, отсутствующий каталог и каталог без репозитория.
Проверены 42 native-теста, 18 Git workspace-тестов, Clippy обеих Rust-сборок
с `-D warnings`, cargo fmt и diff check.

Добавлена левая панель веток по образцу repository rail из gitoui. Разделы Local
и Remotes, поиск по полному имени, дерево по `/` и плоский список, сворачивание
групп, отметка текущей ветки, tooltips с полным ref/upstream/tracking. Панель можно
скрыть или изменить ширину мышью/клавиатурой (180–400 px, default 240). Её локальные
настройки сохраняются при переключении вкладок, но не после перезапуска.
File panel теперь выбирает ориентацию по ширине оставшегося контейнера.
Новый read-only метод `git.branches` возвращает все local/remote tips независимо
от страниц `git.log`, исключает symbolic aliases (`origin/HEAD`) и сообщает
detached/unborn HEAD. Общие DTO, registry RPC, Tauri и AppTauri обновлены.
Нажатие на ветку выбирает её tip в графе и открывает список файлов, не выполняет
checkout. Для незагруженного tip начинается fresh snapshot и поиск по страницам.
Поиск родителей обобщён до `commitNavigation`, поддерживает Cancel и игнорирует
поздние ответы. Ошибка branch read не скрывает историю и сохраняет старый список.
Добавлены `test-branches.mjs` и реальный Git fixture для branch API.
Проверены Fable/Vite, 15 frontend-скриптов, 17 Git workspace-тестов, 42 native
Rust-теста (плюс ignored child helper), Clippy обеих Rust-сборок с `-D warnings`,
Fantomas, cargo fmt и diff check.
В браузере на изолированном IPC fixture проверены обе темы, поиск, tree/list,
переход к tip за первой страницей, раскрытие поиска без потери свёрнутых групп,
drag/клавиатурный resize, скрытие панели и смена ориентации file panel при сужении.
Нативный WebView не запускался; пользовательская БД не использовалась.

Добавлено единственное право записи в БД на экземпляр приложения. Migration
`0003_database_owner.sql` повышает `user_version` до 3; singleton `database_owner`
содержит PID, время старта, путь executable и случайный instance token. `sysinfo`
проверяет процесс по PID и его идентичность. Дополнительно `File::try_lock` на
`projlaunch.writer.lock` удерживается до закрытия SQLite: ОС снимает lock при kill/
abort, а новый владелец заменяет оставшуюся строку в SQL-транзакции. Повторное
использование PID или недоступность информации о процессе не создают вечной блокировки.
Lock-файл не удаляется: удаление работающего lock-файла может создать два lock inode.
Только владелец выполняет migrations/import и записи. Остальные открывают SQLite
с `SQLITE_OPEN_READ_ONLY`; даже прямой SQL через их connection не может писать.
При одновременном первом запуске reader ждёт инициализации до 5 секунд; если первый
владелец исчез до публикации marker, ожидающий экземпляр может захватить lock.
Готовый reader не повышает права автоматически — нужен перезапуск.
IPC `get_storage_access` возвращает `{canWrite, ownerPid}` перед восстановлением
workspace. UI показывает режим, блокирует редактирование, не сохраняет lastOpened/
workspace, но оставляет доступными IDE launch, Git и временные вкладки/панели.
На Tauri Exit storage worker обрабатывает Shutdown, освобождает marker только по
своему token и закрывает SQLite до подтверждения; Drop остаётся запасным cleanup.
Регрессии проверяют настоящую read-only SQLite connection, конкурирующие старты,
миграцию v2, устаревший/reused PID, shutdown и принудительный kill дочернего процесса
с последующим открытием на запись. Child helper помечен ignored и запускается
тестом восстановления автоматически, только с временной БД.
Проверены 42 Rust-теста (ignored child helper запускается родительским тестом),
все 14 frontend `test-*.mjs`, Fable, Vite, Clippy с `-D warnings`, форматирование
и diff check. Read-only banner и disabled edit проверены через React SSR;
нативный WebView для этого изменения не запускался.

Хеши родителей в file panel и заголовке diff стали кнопками (мышь, Enter/Space).
Переход выбирает родительский commit, закрывает прежний diff, загружает его файлы
и прокручивает граф к выбранной строке. Для merge доступны все родители; выбор
базы сравнения в `diff:` остаётся отдельным действием. Если родителя нет среди
загруженных строк, `parentNavigation` догружает страницы существующего snapshot
через `git.log` до совпадения полного OID. Cancel прекращает дальнейшую догрузку;
уже выполняющийся read может завершиться. Новый выбор/другой parent/закрытие вкладки
не позволяют поздним ответам переключить выбор. Ошибка/конец истории сохраняют
текущий commit и показывают сообщение; повтор по хешу начинает fresh snapshot.

одновременно. Относительный путь карточки требует замены на абсолютный;
относительные пути внутри workspace/solution считаются от файла определения.
SSH и WSL проверяются в соответствующем endpoint. В БД связи не создаются.

Git-сервер запускается лениво при первом Git-запросе к endpoint; удалённый поиск
репозиториев также выполняется через сервер. Tauri управляет отдельным stdio-клиентом
и процессом для каждого endpoint и завершает их при отключении/выходе.
Каждая проверка открывает репозиторий на своей текущей сессии;
после сбоя следующая проверка переподключается, старые repoId не переиспользуются.

## Цель и принятые решения

Развиваем существующий Tauri + Fable launcher постепенно, сохраняя запуск
проектов в IDE. Итоговая цель — Git-клиент для Windows, WSL и удалённых машин.
Пользователю нужен единый интерфейс с устойчивым расположением графа истории,
списка файлов и diff, без постоянного переключения вкладок и изменения размеров.
Нужны интерактивный граф и сохранение выбранного репозитория/положения панелей.

- Git выполняется отдельным Rust-сервером на машине, где находится репозиторий,
  включая локальный режим.
- Выбран `json-rpc-rs + axum`: один реестр обработчиков для stdio и сетевых
  адаптеров. `jsonrpsee` рассматривался для сравнения, не выбран backend.
- Tauri Rust управляет процессами и подключениями; Fable вызывает типизированные
  обёртки AppTauri. Детали транспорта не должны попадать в UI Git-операций.
- Один launcher-проект может включать несколько Git-репозиториев (например,
  VS Code workspace); один репозиторий может входить в несколько проектов.
- SQLite через rusqlite принадлежит приложению; Git-серверу база проектов не нужна.
- Целевая последовательность: локальный stdio → status/log/diff → UI с графом →
  WSL/SSH stdio → bootstrap и защищённый HTTPS/WSS с настраиваемым портом.
  WSL/SSH stdio и bootstrap реализованы; отдельный сетевой API остаётся будущим этапом.

## SQLite: текущее поведение

База — `appDataDir/projlaunch.db` (на Windows обычно
`%APPDATA%/com.projlaunch.app/projlaunch.db`). Одним соединением владеет отдельный
поток; очередь Tokio ограничена, ответы идут через oneshot. Включены foreign keys
и busy timeout 5 секунд. Инициализация предшествует выполнению команд.

Схема (`PRAGMA user_version`, сейчас 3) и legacy import выполняются отдельными
транзакциями только у владельца OS lock. Reader пропускает оба шага.
Импорт читает все обычные файлы непосредственно из старого `projects/`, независимо
от расширения. Поддерживаются serde Remote objects, старые Thoth-массивы,
отсутствующий/null remote и UTF-8 BOM. Исходные строки дат сохраняются.

Записи и маркер `legacy_projects_v1` фиксируются одной транзакцией под write-lock.
Ошибки JSON/чтения, пустые ID, дубли ID и конфликты с БД отменяют весь импорт;
ошибка с путём показывается в UI. После исправления нужен перезапуск. При ошибке
инициализации чтение/запись блокируются, а не возвращают пустой список.
Неизвестная более новая версия схемы отклоняется без понижения.

Исходные файлы не изменяются, не перемещаются и не удаляются. После успеха база —
единственный рабочий источник, старые файлы больше не перечитываются. Без старого
каталога создаётся пустая БД с маркером. База без маркера повторяет попытку импорта.
Не удалять пользовательскую БД ради повторения импорта: в ней могут быть новые данные.

IPC сохранён: `get_projects`, `open_project`, `rewrite_project_file` (сохраняет
теперь в SQLite). F#-обёртка называется `saveProject`; форма передаёт `pd.id`.
Debug-проекты не маскируют ошибку загрузки в Tauri.

## Git API: текущее поведение и границы

Полный контракт и примеры — в [руководстве сервера](crates/git-server/README.md).
Методы: `server.hello`, `project.discover`, `repo.open`, `git.status`, `git.branches`,
`git.log`, `git.diffFiles`, `git.diff`, `git.cancel`. NDJSON, object params, обязательные request ID и
caller-generated `operationId` для операций. Batch отключён, notifications
не имеют побочных эффектов. Stdout содержит только RPC, диагностика — в stderr.

- `repo.open` принимает абсолютный каталог внутри worktree, определяет root,
  gitDir/commonDir и возвращает временный repoId. Bare repo не поддерживается.
  repoId и cursor принадлежат своей сессии и недействительны после reconnect.
- Status использует porcelain v2/NUL; разделяет index/worktree, renames,
  untracked и conflicts. Unicode поддерживается; non-UTF-8 paths пока отклоняются.
- Log возвращает OID, родителей, автора, даты, subject, refs; порядок топологический.
  Snapshot фиксирует начальные OID и refs, новые коммиты не сдвигают следующие страницы.
Страница по умолчанию 100, максимум 200; до 1024 начальных OID (передаются Git через stdin,
чтобы не превышать лимит командной строки Windows). Курсоры живут
  до 5 минут или вытеснения, максимум 128. Traversal пока использует `--skip`.
- Diff: unstaged index→worktree, staged HEAD→index, commit parent→commit.
  Для merge обязателен явный родитель (нумерация с 1); root использует empty tree
  соответствующего object format. Сначала список файлов, затем patch выбранного
  пути; rename source определяет сервер. Untracked preview и binary flags отдельны.
- Patch/preview ограничен 128 KiB с флагом truncated. Обычный stdout Git — до
  8 MiB, stderr — до 64 KiB; timeout процесса 30 секунд. До 8 Git-процессов.
  Аргументы передаются массивом без shell, pathspec literal; external diff/textconv
  отключены. При отмене/тайм-ауте/лимите сервер останавливает и дожидается процесса.
- На соединение до 32 запросов плюс 4 места для отмены, очередь ответов 16,
  frame до 1 MiB. Client timeout 90 секунд; timeout закрывает соединение.
- HTTP/WS сохранён под feature `network`, не включён в обычную сборку sidecar.
  Это development loopback-адаптер, а не готовый удалённый endpoint.

Синтетические fetchDemo/watch/unwatch из прототипа не перенесены. Нет Git-записей,
watchers, standalone TLS/auth или постоянных repository bindings в БД.
WSL/SSH deployment реализован, SSH использует аутентификацию OpenSSH.

## Сборка Git sidecar

Логика находится в `build/GitServer.fs`, включённом в `build/build.fsproj`.
Ранее использовавшийся `scripts/build-git-server.mjs` удалён; не восстанавливать его.

```powershell
npm run build:git-server
npm run build:git-server -- --release
# Альтернатива через Windows helper:
.\build.bat build-git-server
.\build.bat build-git-server --release
```

npm-обёртка запускает `build.bat build-git-server` и передаёт ему аргументы, включая `--release`.
В `build/build.fsproj` остаются оба фреймворка: `net10.0;net11.0`.
Выбор фреймворка выполняет только `build.bat` по версии SDK; выбранное значение используется для публикации и пути к исполняемому файлу.
Target берётся из `TAURI_ENV_TARGET_TRIPLE`, иначе из `rustc -vV`.
Бинарник копируется в `src-tauri/binaries/project-launch-git-server-<target>[.exe]`.
Tauri externalBin размещает его рядом с приложением.

`npm run dev` подготавливает debug sidecar; `npm run build` — release sidecar
перед Fable/Vite. Перед прямой Cargo-сборкой Tauri сначала собрать sidecar.
При переносе portable ZIP сохранять каталог `binaries/` с обоими серверами рядом
с GUI. Для legacy layout локальный `project-launch-git-server.exe` лежит рядом с GUI;
для WSL/SSH также нужен bundled Linux-бинарник.

Собранный sidecar проверен чтением основного repo: hello/open/status/log/diffFiles/

В прежней песочнице .NET блокировался при чтении реестра, Git fixture-тесты —
при записи `.git/config` временных репозиториев, сеть Cargo — при DNS.
Соответствующие проверки успешно запускались вне песочницы с разрешением.
Это ограничения среды, не повод менять код. Настройки старых локальных кешей
не требуются на другом ПК. Некоторые исходники используют CRLF; для проверки
whitespace использовался `git -c core.whitespace=cr-at-eol diff --check`.

## Следующий этап

Список сверён с кодом 25 октября 2026 года. Конкретную задачу выбирать по текущему
запросу пользователя; делать по одному крупному изменению.

### Незавершённые функции

- Удаление проекта из launcher: нет UI-действия и команды storage/IPC.
  Удаление должно затрагивать запись каталога и её связи, сохраняя файлы проекта
  и репозитории на диске.
- Watchers/subscriptions для автоматического обновления Git при изменениях.
  Сейчас работают ручной Refresh, обновление по фокусу и проверки после
  загрузки/сохранения проектов; наблюдения за файлами и refs нет.
- Подключение отмены выполняющегося Git-запроса к UI. `git.cancel` уже реализован
  в сервере, Tauri и `AppTauri.Git`, но frontend его не вызывает.
  `CancelCommitNavigation` прекращает дальнейшую загрузку страниц; текущий read
  может завершиться. Нужна связка UI с operationId и серверной отменой.

### Предложенные архитектурные этапы

Постоянная модель связей пока не реализована; точную SQL-схему ещё нужно определить:

- `Project` — launcher-каталог, solution или workspace.
- Постоянный `Endpoint` — среда/сервер и настройки подключения. Runtime Endpoint
  Local/WSL/SSH уже есть; сейчас настройки берутся из проекта и workspace state.
- `RepositoryBinding` — постоянные id, endpointId и путь worktree на endpoint.
  Разные worktree — разные bindings.
- `ProjectRepository` — связь projectId/repositoryBindingId, необязательное
  отображаемое имя и порядок; один repo может быть связан с разными проектами.
- Будущие SQL-таблицы: endpoints, repositories, project_repositories.
  Удаление проекта удаляет связи, а не репозитории на диске.
- Runtime connectionId/repoId не заменяет постоянный binding.
  Не создавать Git bindings автоматически при legacy SQLite import.
  Использовать уже реализованное обнаружение roots для каталогов, VS Code
  workspace и SLN/SLNX; постоянные связи в БД оно сейчас не создаёт.

Отдельный production HTTPS/WSS API с настраиваемым портом остаётся будущим этапом:
нужны аутентификация, credentials/rotation, TLS trust/bootstrap и изоляция сессий.
Текущий HTTP/WS адаптер — development loopback под feature `network`.
Доставка/проверка/обновление сервера в WSL и SSH уже реализованы; SSH использует
OpenSSH для аутентификации, шифрования и проверки host key.

### Известные ограничения вне утверждённой очереди

Эти пункты не имеют отдельного согласованного этапа реализации:

- Ширина/видимость панели веток, фильтр, tree/list и свёрнутые группы не сохраняются
  после перезапуска (`Branches.fs` держит их в локальном состоянии компонента).
- Пути Visual Studio зашиты в коде; remote launch рассчитан на VS Code.
- Удалённый Git поддерживает только Linux x86_64 glibc; Windows/macOS/ARM64

- `src-test/Tests.fs` содержит только placeholder xUnit-тест. Реальные проверки

- Git-операций записи (stage/commit/checkout и других) нет; их состав и порядок
  реализации не определены, текущий Git API предназначен для чтения.

### Незавершённые проверки

- Подтвердить устранение периодического падения WSL `0xC000070A`: изменение
  перенаправления потоков проверено, исходный сбой не был воспроизведён.
- Проверить Git UI и восстановление workspace в нативном WebView, включая GUI

### Правила продолжения

- Сохранять launcher и возможность открывать проекты в IDE.
- Использовать `AppTauri.Git`, не переносить stdio/процессы в UI.
- Сохранять защиту от устаревших ответов через repo/selection/generation.
- После reconnect открывать repo заново, сбрасывать старые cursor/repoId.
- Сохранять выбор родителя merge для diff и обработку binary/truncated/empty states.

## Происхождение и зависимость JSON-RPC

Начальные SQLite и JSON-RPC эксперименты выполнялись вне основного репозитория.
Их необходимые реализации уже перенесены; исторические sandbox-копии и локальная
история baseline-коммитов не нужны для дальнейшей работы и не включены в Git.
Сравнение jsonrpsee и json-rpc-rs было функциональным, не бенчмарком производительности.

Выбранный форк: [slyshykO/json-rpc-rs](https://github.com/slyshykO/json-rpc-rs),
ветка `fix-rpc-protocol-and-axum`, закреплённый commit
`226e48afcc9557adf9b2ce04c72a27a37858be15`.
[Upstream PR #2](https://github.com/pyk/json-rpc-rs/pull/2).
Перед сменой зависимости проверить актуальный upstream статус; не считать PR
слитым по этому handoff. Исправления: неверные параметры → -32602, notification-only
batch без пустого ответа, комментарии feature axum и примеры документации.
В старом эксперименте прошли 84 интеграционных теста и 9 doctests форка с локальными
Windows-обходами; это историческая проверка, не текущая CI-гарантия.

Документ фиксирует решения и выполненную работу, а не дословную историю чатов.
Для нового чата достаточно просьбы: «Прочитай CODEX-HANDOFF.md и продолжи
следующий этап, сохранив мои текущие изменения». После этапа обновлять текущий
статус и оставшиеся задачи здесь; Git сохраняет предыдущие версии документа.
